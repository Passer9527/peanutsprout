# 国际化（i18n）

> 适用范围：Web 端与桌面端界面。由 `@peanutsprout/i18n` 共享包提供，桌面端复用同一套界面，因此**桌面端自动获得同样的多语言能力**。

## 1. 支持的语言

| 代码 | 语言 | 自称 | 说明 |
| --- | --- | --- | --- |
| `zh-CN` | 简体中文 | 简体中文 | **源语言**，也是默认语言 |
| `zh-TW` | 繁体中文 | 繁體中文 | 台湾/香港/澳门地区写法 |
| `en` | 英文 | English | |
| `ru` | 俄语 | Русский | 复数规则最复杂（one/few/many） |
| `ja` | 日语 | 日本語 | |
| `ko` | 韩语 | 한국어 | |

**默认语言是简体中文**。浏览器偏好只有在能映射到上表时才生效：德语环境会落到简体中文，而不是自动变成英文 —— 这是需求「默认为中文」的直接体现。

语言优先级：用户显式选择（`localStorage`）→ 浏览器语言（`navigator.languages`）→ 简体中文。

## 2. 用户怎么切换

- **顶栏**：地球图标 → 弹出语言列表（窄屏只显示图标）。
- **设置页**：「界面语言」下拉框，带当前语言说明。

两个入口共用同一个状态源，切换后**立即生效**并写入 `localStorage`（键 `peanutsprout.locale`），刷新后保持。语言列表里每一项都用**该语言自己的文字**书写（简体中文 / English / Русский / 日本語 / 한국어），这样即使用户误切到看不懂的语言，也能找回来。

### 3.1 键是扁平的，并且有编译期类型约束

键名形如 `命名空间.语义名`（`nav.connections.label`）。`MessageKey` 由**简体中文语言包**推导：

```ts
import { useI18n } from '../state/i18n';
const { t } = useI18n();

t('nav.connections.label');        // ✅
t('nav.connection.label');         // ❌ 编译期报错：键名不存在
```

这是刻意的设计：拼错键名应当是**构建失败**，而不是上线后界面上出现一串键名。扁平结构还让「语言包是否漏译」退化成比较两个字符串数组这一件简单事。

### 3.2 插值

```ts
t('common.countRows', { values: { count: 5 } });   // '5 行'
t('language.changed', { values: { name: 'English' } });
```

模板写 `{count}`。两个细节值得注意：

- **未提供的变量原样保留**（显示 `{name}` 而不是 `undefined`），漏传能一眼看出来；
- `{{` / `}}` 可以转义出字面花括号，所以文案里能安全地写 `{"a":1}` 这类 JSON 示例。

### 3.3 复数走 `Intl.PluralRules`，不是 `count > 1`

中文、日文、韩文任何数量都只有一种形式；英文有 `one`/`other`；**俄语有 `one`/`few`/`many`**：

| 数量 | 俄语类别 | 形式 |
| --- | --- | --- |
| 1 | `one` | 1 файл |
| 3 | `few` | 3 файла |
| 7 | `many` | 7 файлов |

因此复数**必须**交给 `Intl.PluralRules` 判定。语言包里的写法是「基准键 + 后缀」：

```ts
'common.countRows': '{count} 行',            // 无后缀 = other，中文/日文/韩文只需要这一条
'common.countRows.one': '{count} строка',    // 俄语等语言按需补充
'common.countRows.few': '{count} строки',
'common.countRows.many': '{count} строк',
```

调用时只要传 `count`，引擎会自动注入 `{count}` 变量并挑选形式：`t('common.countRows', { count: 3 })`。

> **易错点（本项目真实踩过）**：必须用 `{ count: n }` 这个专门选项，**不能**写成 `{ values: { count: n } }`。
> 后者只是把 `{count}` 插值进去，**复数选择根本不会触发** —— 俄语环境下会永远显示基准形式（`5 строк` 对了，
> `1 строк` 就错了，而且这种错误在中文/日文/韩文环境里完全看不出来）。提交前可用
> `grep -rn "values: { count" apps/web/src` 自查，命中即为漏改。
> 同时含其它占位符时两者可以并存：`t('viz.table.summary', { count: rows.length, values: { limit } })`。

### 3.4 回退链

目标语言缺键 → **回退到源语言简体中文**（不是英文）→ 仍缺则返回 `defaultValue` → 最后返回**键名本身**并触发 `onMissing` 上报。

返回键名而不是空串，是为了让问题一眼可见：空着会让人以为「这里本来就没内容」。

### 3.5 服务端错误按错误码本地化

服务端的 `error.message` 只有中文。客户端**不直接把服务端文案当主文案显示**，而是按稳定的 `error.code` 取当前语言的文案：

```ts
const { localizeError } = useI18n();
localizeError({ code: 'READONLY_VIOLATION', message: '当前连接为只读模式' });
// → 俄语环境下输出俄语文案
```

服务端原文不会丢，它仍作为「原始信息」保留在错误详情里，便于排查 —— 技术细节不做机器翻译。

同理，服务端返回的**中文 `label`（数据库类型、权限项、审计动作、图表类型）一律不直接显示**，而是按稳定的 `code`/`type` 去 `meta` 命名空间取当前语言的展示名。

## 4. 怎么加一条文案

1. 在 `packages/i18n/src/messages/zh-CN/<命名空间>.ts` 里加键（**先加简体中文**，它是权威源）。
2. 组件里 `t('命名空间.键')`。键名写错会在编译期报错。
3. 在**其余五种语言**的同名文件里补上同一条键。
4. 跑测试：

```bash
pnpm --filter @peanutsprout/i18n typecheck
npx vitest run packages/i18n
```

`catalogs.test.ts` 会检查：六种语言是否齐全、有无漏译、有无僵尸键、**插值变量是否与源语言完全一致**（漏掉 `{count}` 是最常见的线上事故）、复数形式是否按该语言的真实规则成套提供、繁体/俄语/日语/韩语是否真的用了对应文字（防「复制粘贴中文」）。

## 5. 怎么加一种语言

1. `packages/i18n/src/locales.ts` 的 `LocaleCode` 与 `SUPPORTED_LOCALES` 里加一项（`nativeName` 必须用该语言自己的文字书写）。
2. 复制 `messages/zh-CN/` 为 `messages/<新代码>/`，逐文件翻译。
3. 在 `messages/index.ts` 里注册。
4. `locales.ts` 的 `normalizeLocale()` 里加上该语言前缀的识别分支。
5. `catalogs.test.ts` 顶部的「需求点名语言」列表按需更新，并跑一遍测试。

## 6. 刻意的取舍（诚实说明）

| 项目 | 现状 | 原因 |
| --- | --- | --- |
| **日期时间格式** | 保持 `YYYY-MM-DD HH:mm:ss`（ISO 风格），不随语言变成 `2025年9月16日` 或 `16/09/2025` | 这是数据库管理工具，审计日志与连接列表里的时间戳必须**无歧义且可排序**。同一列里混着美/欧含义相反的 `03/04/2025`，比「不够本地化」危险得多。**数字**仍然照常本地化（英文 `1,234.5` / 俄语 `1 234,5`）。 |
| **CLI 输出** | 仍为中文 | 面向运维/开发者的命令行工具，不是终端用户界面。`@peanutsprout/i18n` 可以直接被 CLI 复用（`defaultI18n` 即为该用途准备），属于后续工作。 |
| **服务端日志** | 仍为中文 | 日志面向开发者排查，不做机器翻译。 |
| **文档** | 只有中文 | PRD 与文档全集以中文为权威版本。 |
| **数据库/SQL 关键词** | 不翻译 | `SELECT`、表名、列名、类型名属于用户数据与技术标识，翻译会造成误操作。 |
| **专有名词** | `花生苗`、`飞哥`、`AGPL-3.0` 等保留原文 | 产品名与许可证名不翻译。 |
| **作者落款** | `auth.login.footer` / `admin.settings.about.authorValue` 在**所有语言**里都保留 `飞哥 · 微信 6731663` | 这是人名与联系方式，属于标识而非文案。翻译成 `Feige · WeChat` 反而让用户对不上人；且与各语言 `app.copyright` 保持一致。（繁体中文语言包里写作 `飛哥`，这是该语言的自然写法。） |
| **厂商名** | `通义千问`/`智谱 AI`/`月之暗面` 在非中文语言里写作 `Qwen`/`Zhipu AI`/`Moonshot AI` | 这些厂商本身有官方拉丁名，中文名只在中文界面有意义。数据库厂商同理：`金仓 KingbaseES` → `KingbaseES`，`达梦 DM` → `Dameng DM`。 |
| **客户端的 `useI18n` 守卫错误** | 仍为中文（`useAuth 必须在 AuthProvider 内部使用`） | 这是给开发者看的框架不变式，永远不会渲染给终端用户，与代码注释同一性质。 |

## 7. 自动化保障

- `npx vitest run packages/i18n` —— 引擎单测 + 语言包完整性测试（当前 **61 个测试全绿**：`i18n.test.ts` 21、`key-safety.test.ts` 4、`catalogs.test.ts` 36）。
- `pnpm verify` 的「国际化（i18n）」小节会检查：六种语言是否齐全、逐语言有无漏译/僵尸键、翻译运行时是否真的返回译文（而不是键名）、默认语言是否为简体中文，并**扫描 `apps/web/src` 里是否还有硬编码的中文 JSX 文本**（注释不算；当前扫描 32 个文件，0 处命中）。
- `key-safety.test.ts` 专门防止一类**静默失效**：如果源语言包被写成 `const zhCN: MessageCatalog = {...}`，TS 会把键类型放宽成 `string`，`t('随便什么')` 都会编译通过 —— 键名约束会在没人察觉的情况下彻底消失。该测试用类型断言把这个坑钉死。
